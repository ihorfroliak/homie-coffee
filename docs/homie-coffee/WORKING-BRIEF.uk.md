# Homie Coffee — робоча карта

Оновлено 30.10.2026. Власник рішень — Ігор. Дослідження, обговорення, промпти й розробку ведемо
в цьому чаті Codex; погоджені результати зберігаємо в репозиторії. Claude не є обов'язковим
учасником. Це навігаційний огляд; статуси рішень визначає [реєстр](01-assumptions-questions-decisions.md).

## Що будуємо і чому це може працювати

Робоча гіпотеза: доступна specialty-кава для людей, яким потрібна смачна чашка без складного
ритуалу вибору. Продаємо зрозумілий смак, відповідність способу заварювання й зручне повторне
замовлення. Позиціонування D-003 і бізнес-модель D-004 ще відкриті.

Початкове припущення — private label: польський партнер обсмажує та пакує каву під нашим брендом.
Ми відповідаємо за пропозицію, продаж, сервіс і повторну покупку. Власна обсмажувальня, імпорт
зеленого зерна й самостійне перепакування не входять у поточну гіпотезу MVP. Екран «черга
обсмажування» з нового дизайну збережено як концепцію, а не як зміну моделі постачання.

Два можливі канали:

- **B2C:** покупець обирає каву за смаком і методом, бачить повну суму до оплати, отримує партію
  з достовірною датою обсмажування та зрозумілим рецептом. Мета — повторна покупка, а не лише
  перше замовлення. Платне залучення B2C не проходить поточну модель; це висновок за її
  припущеннями, не універсальний доказ, що B2C неможливий.
- **B2B:** гіпотеза для підприємств Кракова/околицях, які вже мають кавомашину: постачання зерна
  без оренди й обслуговування техніки, спочатку з передоплатою. B2B-first (D-017) ще не погоджено;
  маржинальність не доведена. Значення B2B у моделі залишаються `unresolved`.

## Логіка процесів — пропозиція для наступної специфікації

| Процес | Послідовність | Що необхідно визначити до реальної реалізації |
|---|---|---|
| Постачання | пропозиція партнера → зразки → обрана кава → партія → приймання → доступний залишок | закупівельна база net/gross, MOQ, пакування, строки, придатність, хто зберігає й відправляє |
| Каталог | товар → варіант ваги/помелу → партія → доступність → погоджена ціна | справжні фото й опис, перелік SKU, ціна/податки, правила помелу |
| Покупка | вибір → кошик → доставка/контакти → підтвердження суми → очікування оплати | гостьова покупка, доставка, купони, правила зміни ціни, потрібні згоди |
| Оплата | очікує → підтверджена / невдала / прострочена | джерело підтвердження, повторні повідомлення, грошова точність, термін резерву |
| Виконання | підтвердження оплати → резерв → комплектація → відправлення → доставлено | дефіцит після оплати, часткове виконання, скасування, повторне відправлення |
| Документи й повернення | підтвердження → документ → корекція/повернення за потреби | бухгалтер перевіряє VAT/KSeF/рахунки; стани повернення коштів окремі від доставки |
| Повтор | рецепт → досвід покупця → відгук → повторне замовлення | дозвіл/підстава повідомлень, частота, справжня повторюваність і витрати сервісу |
| B2B | контакт із дозволу → потреба → пропозиція → погодження → передоплата → відправлення → повтор | доступна ціна, мінімальний обсяг, індивідуальні умови, позитивна маржа |

Стани оплати, виконання і повернення не слід зводити в один статус. Натискання кнопки
«оплатити» не доводить оплату. Одна й та сама подія платіжного сервісу не повинна створювати
два замовлення, двічі списувати залишок або дублювати документ. Це запропоновані інваріанти
для специфікації, а не реалізований backend. Точний порядок резерву до/після оплати ще потребує рішення.

Прибутковість рахуємо після кави, пакування, платежу, комплектації, доставки, списань,
повернень, сервісу й залучення. Тепла аудиторія не означає нульовий CAC: є час, зразки та доставка.
Модель не підміняє реальних комерційних пропозицій. Дані й висновки — у [Gate 0](18-commercial-feasibility-gate.md)
та [моделі](model/unit-economics.mjs); нові ринкові числа цим імпортом не додаються.

## Що погоджено, а що лишається рішенням

| Погоджено | Ще не погоджено / не підтверджено |
|---|---|
| D-006: Next.js/TypeScript, PostgreSQL/Prisma, модульний моноліт, owner TOTP та журнал змін; технологічний вибір не дорівнює запуску | D-003–D-005: позиціонування, бізнес-модель, MVP |
| D-023: локальний Admin Option 1 з макетними даними | D-007/D-008: вимірювання реклами й дорожня карта |
| D-025: працюємо тут без обов'язкового Claude | D-016/D-022: позиція щодо VAT та консультації; попередні податкові записи не є актуальною юридичною перевіркою |
| D-026: зберігаємо й інтегруємо Shop/Admin, досліджуємо патерни інших Homie-продуктів | D-017–D-020: B2B-first, бюджет валідації, надсилання запитів постачальникам, пілотна партія |
| Польська основна, англійська друга — поточне припущення A11 | D-021: перевірка торговельної марки; реальні SKU/ціни/умови доставки |

Умова D-024 перед production: щонайменше три пропозиції обсмажувальників з явною базою net/gross,
перевірена бухгалтером податкова позиція та погоджені бізнес-рішення. Контакти, закупівлі,
рекламні витрати й публікація не були автоматично дозволені словами «будемо продавати каву».
Прототип і специфікацію продовжуємо вже зараз.

## Як використаємо нові дизайни

Вхід до локального прототипу має три розділи: **Магазин**, **Admin Lab**, **Операційна панель**.
Експорти зберігаються з контрольними сумами, походженням і описом адаптації у
[design/sources/2026-10-30](../../design/sources/2026-10-30/README.md).

| Ідея | Навіщо | Поточний статус |
|---|---|---|
| Квіз за смаком і методом | зменшити складність вибору | є локальна демонстрація; якість рекомендацій не перевірена |
| Картка партії, помел, вага, ціна за кг | пояснити продукт і порівняння | макет; всі значення й обіцянки потребують перевірки |
| Рецепт після покупки, калькулятор | допомогти отримати добру чашку | локальне демо; рецепти ще не фактчекнуті |
| Повторити замовлення | скоротити шлях повернення покупця | кандидат для MVP, не автоматичне погодження |
| Підписка з паузою/пропуском/скасуванням | регулярність без зайвих дій | пізніша гіпотеза A9, не обов'язкова для MVP |
| Сліпа дегустація, workshops, referral credit, відгуки | дослідити навчання й органічний попит | ідеї; ціни, попит і економіка не підтверджені |
| Планування власного обсмажування | можливе майбутнє виробництво | поза поточною private-label моделлю |
| Події й листи D0/D3/D10/D21/D45 | зрозуміти шлях та повернення клієнта | статична концепція; реальні події/листи не надсилаються |

Магазин, Admin Lab і старий Dashboard поки **не мають спільних даних**. Фото товарів у ZIP
відсутні. Демо-кошик починається з однією пачкою, усі зміни скидаються після оновлення.

## Що беремо від HeyHomie та Homies

З наданих HeyHomie-макетів реально спостерігаються таймлайн, видимий статус, наступна дія,
узгоджені коротка/детальна картки й окремі специфікації станів, прав, синхронізації та аудиту.
Для кави пропоную застосувати це до замовлень, партій, оплати й роботи оператора. Візуально
зберігаємо Manrope, темний ink і м'ятний акцент; розбіжність відтінків нового/старого макета
потребує окремого рішення, а не прихованої заміни.

Це аналіз переданих дизайнів, не аудит живих систем. Homies-specific патерни ще треба підтвердити
за конкретним джерелом; не приписуємо йому функцій без перевірки. Не переносимо клієнтську базу,
авторизацію, прайси, правила клінінгу чи автоматичний cross-marketing між продуктами.

## Як працюємо далі

1. Тут формулюємо питання й досліджуємо. Зовнішні твердження — з джерелом, датами й рівнем
   підтвердження у `sources.md`. Надані Claude-тексти — вхідні гіпотези, не достовірні факти.
2. Для кожного рішення відокремлюємо рекомендацію Codex від явного рішення Ігоря.
3. Погоджений невеликий сценарій → компоненти/стани → зміни → перевірка → запис результату.
4. Наступний логічний крок у прототипі: **каталог → товар → кошик → demo-підтвердження**,
   із клавіатурою, фокусом, пустими/помилковими станами й PL/EN. Окремо — контракт подій;
   потім узгоджений показ demo-замовлення в операційній панелі.
5. Комерційний шлях паралельно: підготувати конкретні пропозиції для рішень D-019/D-022,
   після дозволу отримати докази, перерахувати модель й затвердити перший продаж.

### Промпт для наступного кроку — чернетка, не автоматичний запуск production

> Продовжуй Homie Coffee за AGENTS.md, реєстром рішень і останнім HANDOFF. Працюй у поточному
> Codex-процесі без обов'язкового Claude. Для локального demo підготуй component/state spec
> шляху каталог → товар → кошик → demo-підтвердження. Опиши компоненти, переходи, порожній
> кошик, помел/вагу, помилки, повну суму, клавіатуру, фокус та PL/EN. Відділи пропозиції
> бізнес-правил від погоджених рішень. Збережи наданий дизайн як референс. Спочатку розклади
> великі експорти на перевірювані сценарії, не перенось export-runtime у production.
> Визнач контракт локальних подій і критерії перевірки. Не додавай платежі, облікові записи,
> зовнішні інтеграції чи публікацію. Запусти наявні перевірки, перевір браузер і запиши лише
> фактичні результати. Підготуй одну невелику наступну зміну для Ігоря.
